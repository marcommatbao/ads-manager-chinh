# P6 — bounded attribution source truth

## User-visible reconciliation

The existing `app/(dashboard)/reports/attribution/page.tsx` now includes a compact **Lead/order evidence reconciliation** card (`components/reports/LeadOrderEvidence.tsx`). Its independent read calls `/api/attribution/report?aggregate=1&company=…&range=…`. The platform comparison still calls the separate `/api/attribution` API with its existing filters and behavior. Neither API is a campaign business-attribution binding.

The card uses the page's selected company and 30/60/90-day range. The report route resolves these ranges on the server using the existing platform API's day arithmetic: N days ending yesterday. The response discloses exact UTC day bounds. Existing explicit from/to clients and the legacy detail response remain supported; invalid/calendar-overflow/reversed dates and unsupported ranges fail before store reads. Auth/company/ALL guards run first. ALL resolves only for a single authorized company; multi-company ALL requires a selection.

The aggregate response explicitly projects counts/coverage/source metadata, never matched/unmatched detail rows or lead/order keys, IDs, hashes, click IDs or campaign labels. Counts include won lead **events**, unique eligible orders, matched/unmatched unique orders, ambiguous evidence, excluded duplicate rows, conflicting duplicate keys and currency count. No revenue total is introduced. Duplicate rows are excluded from the unique denominator; conflict keys remain unique unmatched orders and invalidate both rates. Mixed currency invalidates value coverage. Zero denominators yield null coverage.

UI states: loading, request error, session/permission denial, partial source availability, both sources unavailable, successful local empty, available, null coverage, duplicate conflicts and currency limits. Counts are unknown (`—`) when reconciliation is unavailable; null coverage says unknown rather than 0%. Source reasons and actual nullable read times appear separately for orders and leads, alongside range and selected source. The card stays visible if platform comparison fails. Fetches use same-origin authentication, no-store and abort/ignore old responses on scope changes. No provider reads or mutations are introduced by the card/report path. VI/EN keys are in the existing overview namespace; wording is **proposed, pending BA review**.

## Strict source contracts

Orders retain the existing opt-in `readOrdersTruth` from `lib/orders/sources.ts`. No changes to `readOrders`, `readStoredOrders`, ingestion, provider adapters, MBI order-source list or payment/team/type/date filters. Existing MBI business source filters and notify source filters remain intact.

Leads now support `readLeadEvents(company, { strict: true, since, until })`. `lib/leads/source-truth.ts` reads the company-specific event file without any provider/default source fallback. Missing/unreadable, malformed JSON, invalid root/row/matching-field shape and a store at its 20,000-row pruning cap return events null with a safe reason. Invalid/reversed range does not read the file. Successful reads validate the whole store before selecting events in the exact range. Only won events then participate in the report. The one-argument reader and all legacy callers retain their previous behavior; strict attribution never treats the legacy empty-on-error result as evidence.

Both source metadata objects bind company, exact ISO from/to, selected source, status, completeness, scope and nullable readAt. `complete`/`selected_local_store` only certify the local read, never upstream delivery. Lead storage has count pruning and no historical watermark; reaching the cap fails closed. Order requests beyond the existing 120-day retention window or at the 20,000-row cap fail closed. No historical watermark or ingestion timestamp was invented.

readAt is stamped only after bytes are read, including JSON/shape failures, and is null when no store was read. It is not persisted and does not establish upstream freshness. Unavailable either source yields null aggregate totals and coverage; detail clients still receive empty compatibility lists, which must not be interpreted as measured zero. Inspect **both** source.status and leadSource.status. Successful empty local stores yield zero counts with null coverage.

Supported Odoo remains unavailable with completeness_unverified and readAt null: the existing adapter caps its raw query at 5,000 before normalization and exposes no truncation proof. This path does not call it. Unsupported Odoo remains a separate reason. No new provider/config/error diagnostics or raw identity evidence are returned in the aggregate response.

Matching retains click ID → UTM campaign → campaign label priority and ambiguity rules. Identical duplicate evidence contributes one order/value. Conflicting value/currency/matching evidence prevents assigning the unique key, with both rates null, independently of input order. Detail duplicate rows stay marked duplicate_order for compatibility and must not be summed.

**Company/provider/account/campaign binding is NOT ESTABLISHED.** Local reconciliation does not establish campaign ROAS, upstream completeness/freshness, pacing readiness or P7 permission. P7 remains locked. Profit/COGS is outside this slice.
