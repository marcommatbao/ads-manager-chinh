# Transactional execution coordinator foundation

Not wired to execution. Automation stays OFF and `EXECUTION_COORDINATION_UNVERIFIED` remains in approval-store. No existing approval records are imported or consumed by this foundation. The coordinator now enforces SQLite-registered approval authority and current revision/source bindings transactionally. Trusted ingestion and execution integration remain absent; arbitrary incoming objects are not approval evidence.

`ExecutionCoordinator.reserveAndClaim` uses built-in `node:sqlite` and `BEGIN IMMEDIATE`. A single durable row is both reservation and permanent uncertain claim, keyed globally by approval ID. Exact replay returns `already_claimed`, which MUST NOT authorize a provider call. Identity changes fail closed. There is no release or retry API. Outcome bookkeeping never grants execution or frees quota. No provider calls, raw payload storage, environment configuration or business threshold decisions are included.

The internal constructor defaults to `data/automation-execution.sqlite` under app cwd; only trusted server composition/tests may supply another absolute local path. Never expose path configuration via HTTP. Tests use isolated OS temp directories, never app data. This is a single-host local-filesystem coordinator, not cross-host/network-filesystem coordination. All executors must use the same file. Durable hosting requires persistent local storage with appropriate filesystem permissions and backups; SQLite FULL synchronous commits still depend on filesystem/device guarantees. Claims grow without automatic pruning. SQLite uses rollback journaling and a bounded 1500 ms busy timeout; busy/corrupt/storage failures return a sanitized unavailable error.

Campaign exclusion includes company/provider/account/campaign; one claim per UTC day plus policy cooldown. Daily quotas count all providers/accounts per company/UTC day; run quotas count company/run/UTC day. Limits must be explicit finite bounded values (matching current policy bounds); zero caps deny new claims. Policy identity and normalized source scope/hash are mandatory and persisted internally, never returned. Source hashes are supplied opaque values, not inferred algorithms. Request projection excludes unknown properties. Canonical UTC timestamps are required; future source reads, expired requests and persisted future claim clocks fail closed. Replay still requires a currently valid request; expiry never releases its permanent claim.

Runtime verified locally: Node 22.23.2, built-in experimental SQLite 3.51.3. Dockerfile currently uses floating `node:22-alpine` in all stages. Main pulled the image, but a bounded no-network probe could not start because Docker host reported cgroupv2 invalid state while applying resource limits. No resource protection was disabled; no app stack was started. Image SQLite compatibility and future Next standalone wiring remain unverified. A full application build does not prove this dormant module is bundled. Before wiring, verify the actual runtime supports `node:sqlite` without flags and the server-only bundle externalizes the builtin. No dependency was added.

Focused verification: 10/10 tests PASS and scoped ESLint PASS. Tests launch actual competing OS Node processes against the same temporary DB for campaign/daily/run contention, restart replay and identity conflicts. A child killed with SIGKILL inside an uncommitted transaction leaves no phantom claim/quota when reopened. Other checks cover scoped quotas, failed INSERT rollback, cooldown, corrupt DB, busy locks, invalid dates/limits and future clocks. Main full suite before the extra crash test: 239 PASS / 71 skipped; final focused suite and TypeScript rerun pass. Future wiring remains a separate deliverable.

## Absolute budget delta ledger (dormant)

Requests now require decision ID, approval snapshot hash, registry scope/hash, policy revision identity, provider/account/company/campaign, run ID, currency, budget kind and before/proposed budgets. All are bound into immutable claim identity; changing any binding on replay conflicts. Only campaign daily budgets are supported. Budgets must be finite positive safe integers in **minor currency units**. Currency must be an uppercase ISO currency recognized by the runtime ICU currency registry; arbitrary three-letter codes fail closed. Existing decision/provider amounts must be explicitly converted and verified before any future integration; this module never guesses major/minor units or rounds amounts.

Both `maxAbsoluteBudgetDeltaPerDayMinor` and `maxAbsoluteBudgetDeltaPerRunMinor` are mandatory nonnegative safe integers, with run <= day. No business defaults were introduced. Zero budget caps permit only zero delta (mutation caps still apply). Delta is `abs(proposedBudgetMinor - beforeBudgetMinor)`; increases and decreases cannot offset each other. Reservations aggregate by company + ISO currency + UTC claim day, and additionally run ID for the run cap. They span providers/accounts. Different currencies have separate ledgers: there is no exchange conversion or pooled mixed-currency sum. Mutation-count quotas remain company-wide across currencies.

Claim insertion, budget reservation, cap checks and campaign exclusion share one SQLite BEGIN IMMEDIATE transaction. Totals use BigInt addition, avoiding unsafe floating-point sums near MAX_SAFE_INTEGER. Old claims without monetary reservations block new same-company/day claims rather than silently count as zero; existing rows are not backfilled. This is not a production migration.

## Immutable outcomes and reconciliation

`recordOutcome` accepts an internal event ID, claim ID and unknown/timeout/provider_confirmed kind. Unknown and timeout remain `needs_reconciliation`; a claim without any outcome does too. Exact event replay is idempotent, changed event identity conflicts. After a provider-confirmed event, new events conflict; replay of earlier exact events stays idempotent. SQLite triggers forbid UPDATE/DELETE of outcome rows through normal SQL, and a unique partial index allows only one confirmed outcome per claim. This is application bookkeeping, not tamper resistance against a filesystem/database administrator.

Confirmation requires a nonempty opaque provider receipt ID supplied by trusted server code. The coordinator does **not** verify that receipt with a provider. Before activation, a provider-specific verifier must establish authoritative receipt provenance, binding to this exact claim and intended mutation, and sanitize the stored identifier. Observed budget equality is not accepted as execution proof. No outcome releases reservations, permits retry, or removes claims, including confirmed outcomes.

## Activation blockers and validation

The existing executeStoredApproval hard guard is unchanged. No HTTP mutation endpoint, provider call, adapter activation, live-data migration or policy editor change was added. A pure preflight was deliberately not added: a detached preflight cannot close the authorization race against existing JSON approvals/policy/source stores.

**SQLite approval authorization/consumption and revision/source checks now share the claim transaction, as described below.** SQLite coordination is NOT atomic across JSON files. Before activation, trusted ingestion must establish approver rights, decision provenance, snapshot registry/hash, current policy revision/enabled flags, source freshness, budget units and explicit business-approved delta limits, and keep subsequent policy/source invalidations authoritative in SQLite. No default policy currently supplies the new delta limits; missing values deny coordination. Receipt verification and actual beta runtime/storage/standalone-bundle validation remain main-agent work.

Focused validation for this extension: 18 tests passed, scoped ESLint passed. Actual OS processes contest mutation and absolute-delta day/run caps; increasing/decreasing deltas compete without netting. Tests cover monetary/provenance replay mismatch, independent currencies, safe-integer accumulation, rollback of budget insert, restart retention, uncertain quota retention and concurrent conflicting outcome writers. All databases are isolated temporary fixtures. Full application suite/build and beta checks are outside this delivery.

## Server policy limits projection (dormant)

`AutomationPolicy.absoluteBudgetDeltaCapsByCurrency` maps explicit supported uppercase ISO currencies (the same runtime ICU registry as the coordinator) to exactly `maxAbsoluteBudgetDeltaPerDayMinor` and `maxAbsoluteBudgetDeltaPerRunMinor`. Both are nonnegative safe integers in that currency's minor units, with run <= day. Zero allows only zero delta; there are no monetary defaults or currency conversions. Unknown currencies, prototype keys, malformed records, extra cap fields and major-unit field names are rejected. Numeric values carry the declared minor-unit contract; this layer cannot detect an upstream caller incorrectly labeling a major-unit integer.

Legacy policies remain readable with an empty map. Defaults remain draft/OFF with no caps. Draft saves retain the map in policy/audit projections and generate a fresh revision, including cap-only changes. Under the existing file lock and expected-version check, omitted maps from older clients preserve the current map; an explicit empty object clears it, while null/undefined are invalid. The current policy editor spreads the server policy into its save payload, so unrelated edits retain caps without UI changes. It does not provide a cap editor. Saves still force draft/OFF and require subsequent trusted approval outside this step.

`coordinatorLimitsFromPolicy(trustedPolicy, explicitCurrency)` is a pure server helper in the filesystem-backed policy module. It revalidates the policy, requires approved status, nonblank owner, global/apply enabled and an own cap entry for that currency, and projects count/cooldown/monetary limits. A caller must supply policy from trusted storage: this function cannot establish approval provenance from an arbitrary object. It does not read source/approval state, claim quota, import JSON into SQLite, or authorize execution. No call site wires it to execution. The `executeStoredApproval` hard guard remains unchanged. The SQLite current revision registry described below must be maintained by trusted ingestion alongside all other activation prerequisites; a detached projection is not that authority.

Beta access, live Meta tests, runtime deployment validation and activation remain deferred. No migration, provider access, service or environment-secret access is required by this change.

Local verification for the policy extension: 82/82 tests passed across policy validation, draft store, trusted limits helper, policy route, settings-response, execution coordinator and approval-store regression suites (7 files). Scoped ESLint, TypeScript (`tsc --noEmit`) and whitespace checks passed. Tests use temporary policy/audit files and SQLite fixtures, with no beta/provider calls.

## Transactional approval authority (dormant)

All authority tables live in the **same SQLite file** as claims, reservations and outcomes. No HTTP endpoint or JSON importer exists. These methods are trusted internal server APIs, not proof verifiers; callers with access can grant authority. Never forward an HTTP body, arbitrary decision object or caller-provided approver ID to registration. Filesystem/DB administrators remain outside the tamper-resistance boundary.

Trusted ingestion sequence:

1. `registerCurrentPolicy(company, revision)` records the current company policy revision. Exact current registration is idempotent; a superseded revision cannot be reactivated. Every relevant policy change, including disabling apply or switching to draft, must publish a fresh revision before new claims are allowed. A disabled/draft revision must receive no authorizations. This is an explicit revision registry, not a complete SQLite policy editor or policy evaluator.
2. `registerSource(request, sourceExpiresAt)` registers an immutable registry scope, company/provider/account/campaign, policy revision, hash, canonical read time and independent expiry. Reusing a scope with changed binding/expiry conflicts. `invalidateSource(scope)` irreversibly invalidates it; a replacement needs a new scope. The collector must establish hash provenance, source freshness and the allowed TTL; the coordinator does not inspect payloads or infer TTL. Supersession requiring old-source rejection must invalidate the old scope. Expiry is checked during claim even when the approval has a later expiry.
3. `registerAuthorization(request, approverId)` registers a globally unique approval ID and unique decision ID with an immutable canonical request identity, approver and expiry, initially approved. The identity binds all declared request fields, including limits, monetary units, before/proposed budgets, run, source provenance and policy revision; the approval ID is the primary key. Unknown extra properties are excluded. The trusted service must resolve the real decision, verify approver rights and snapshot binding, project current approved/enabled policy limits and establish all business guards before registering. There is no arbitrary `verified` boolean. Exact registration replay is idempotent and **never resets terminal state**. Changed approval identity, approver, or a second approval for the same decision conflicts.

`reserveAndClaim` takes `BEGIN IMMEDIATE` before reading authority/current revision/source and rechecks time after acquiring the write lock. A new claim requires exact immutable identity, approved unexpired authorization, current policy revision and a current matching unexpired source. It transitions approved → consumed in the same transaction as quota checks, campaign exclusion, permanent claim and monetary reservation. Any denial or insert failure rolls everything back, leaving neither quota nor consumption. Replay requires a matching consumed authorization and current source/policy, returns only `already_claimed`, and cannot authorize another provider call. Legacy claims without authority fail closed; no backfill occurs.

`revokeAuthorization(approvalId)` also uses `BEGIN IMMEDIATE`, permits only approved unexpired authority and transitions it to revoked. Against a competing claim, exactly one can commit: revoke wins and claim denies, or claim consumes and revoke denies. Revocation never releases a claim/reservation. SQLite triggers prohibit authorization identity edits/deletion and terminal-state resurrection, and source binding edits/deletion/reactivation. Registration replay does not reapprove revoked or consumed authority.

Integration limit: this transaction protects **only registered SQLite state**. Current JSON policy, approvals, decisions and snapshots remain separate, unchanged and non-atomic with SQLite. A one-time copy or delayed JSON sync would reintroduce stale authority. Activation requires a trusted authoritative ingestion/update protocol for policy changes, source invalidation and approval/revocation; it must not let JSON updates bypass SQLite. No live policy ingestion, approver authentication/authorization service, decision verifier, source collector bridge or provider receipt verifier was implemented. `executeStoredApproval` still throws `EXECUTION_COORDINATION_UNVERIFIED`; apply stays OFF and legacy routes are unchanged. Beta/runtime/storage validation and live Meta tests remain deferred.

Focused verification for this change covers actual competing Node processes for revoke/claim (eight races), revision invalidation and anti-reactivation, source invalidation/expiry, approval expiry, missing authority/identity mismatch, duplicate approval/decision replay, terminal immutability, authorization/reservation insert rollback and denial without quota/consumption. Existing campaign/count/delta/currency/outcome guards remain tested. All databases are temporary fixtures; no real migration, service, network/provider, deploy or full build is run.
